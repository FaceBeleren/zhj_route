# 垃圾收运路线优化项目阶段性汇报

日期：2026-07-02

## 1. 项目定位

本项目面向垃圾收运业务中的路线规划、路线评估和多车辆多路线生成问题，目标是把早期算法研究、旧系统落地经验和当前项目数据能力整合为一个可演示、可迭代、可产品化的路线优化系统。

项目不是从零开始写一个算法 Demo，而是在三个历史来源基础上继续推进：

1. 早期 OneNote 笔记和 Python 脚本：记录了从清华算法、启发式插入算法、车辆排班、时间限制、区域划分等方向的算法思考。
2. 旧垃圾收转运系统 ljszy：曾经落地过单条路线优化，并包含 OD 矩阵、百度算路、路线地图展示等工程经验。
3. 当前 zhj_route 工程：正在把路线评分、单路线优化、多路线生成、地图展示和后续生态集成逐步产品化。

当前阶段的核心工作，是把历史算法思路从“笔记和脚本”整理成可运行的工程能力，并在此基础上继续迭代多路线规划。

## 2. 背景问题

垃圾收运路线优化看似是“点位排序”问题，但真实业务远比简单 TSP 更复杂。

实际需要同时考虑：

- 点位位置和道路距离；
- 点位预计垃圾量；
- 车辆额定载重、最大载重和趟次；
- 起点、终点、停车场、中转站、处理厂；
- 多条路线之间的点位分配；
- 路线是否满足装载率和业务可解释性；
- 地图展示是否使用真实道路折线；
- 历史流水和规划路线之间的一致性评价。

早期算法已经形成了一些重要认识：

- 单纯最近邻不够稳定；
- 只看点到当前点最近，容易局部最优；
- 更合理的基础策略是“全路径插入”：每次尝试把候选点插入当前路线的任意一段，选择增量最小的插入位置；
- 多路线问题的关键不是一条路线怎么排，而是第一条路线何时停止、剩余点如何继续分配、车辆顺序如何影响结果。

因此，当前项目先选择一条工程可落地的路线：先做清晰、可解释、可验证的启发式算法，再逐步加入更复杂约束。

## 3. 当前已完成能力

### 3.1 路线与岗位工作界面

当前前端已经具备基础路线工作界面，可以按项目公司查看路线、岗位、规划点位和流水相关信息。

已有能力包括：

- 按公司加载路线和岗位；
- 查看规划点位池；
- 查看流水记录；
- 查看路线/岗位点位明细；
- 作为后续路线地图展示和路线评分的统一入口。

这部分的意义在于：路线优化不再是一个孤立算法页面，而是放回业务对象中使用。

### 3.2 路线评分

当前项目已经实现了路线评分相关功能，用于比较历史流水与规划路线之间的一致性。

已实现方向包括：

- 基于历史流水分析路线执行情况；
- 使用 LCS、命中率、召回率等指标衡量流水与规划路线的匹配程度；
- 支持公司、路线等维度的评分展示；
- 支持进一步扩展为“流水顺序 vs 规划顺序”的可视化对比。

这部分能力解决的是另一个实际问题：路线优化不能只看生成结果，还需要评估实际执行是否符合规划。

### 3.3 单路线优化

当前已经实现单条路线优化能力。

核心算法是全路径插入：

```text
route = [起点, 终点]
remaining = 中间点

while remaining 不为空:
    遍历每个候选点
    遍历当前路线每一段
    计算插入增量 d(A,P)+d(P,B)-d(A,B)
    选择增量最小的点和插入位置
    插入路线
```

单路线优化支持两类距离来源：

- 直线距离：根据经纬度快速计算；
- 实际道路距离：读取 OD 缓存，缺失时可调用百度补算，失败则直线回退。

地图展示也支持：

- 点位直线；
- 道路折线；
- 原路线和优化后路线的显示/隐藏；
- 轨迹播放；
- 地图最大化展示。

### 3.4 多路线生成

当前已经实现公司级多路线生成。

输入包括：

- 项目公司；
- 公司点位池；
- 额定载重；
- 目标装载率；
- 最大趟数；
- 起点和终点；
- 可选车辆排班信息。

输出包括：

- 多趟路线；
- 每趟路线点位顺序；
- 每趟预计垃圾量；
- 每趟距离和耗时；
- 装载率；
- 已分配和未分配点位；
- Excel 导出结果。

目前的多路线基础策略是：

1. 按当前策略生成一趟路线；
2. 该趟路线达到目标装载率或无法继续插入后输出；
3. 删除已分配点位；
4. 对剩余点位继续生成下一趟；
5. 直到点位分配完毕或达到最大趟数。

### 3.5 多路线规划策略

当前多路线已支持三种规划策略。

#### 直线快速分组

先用经纬度直线距离快速生成多条路线。

特点：

- 速度快；
- 不依赖 OD 矩阵；
- 适合快速得到初始方案；
- 道路真实性较弱。

#### 直线分组 + 道路精排

这是近期新增的两阶段策略。

流程：

1. 第一阶段：用直线距离快速把点位分成多趟路线；
2. 第二阶段：把每一趟路线当成单条路线，在该路线内部用道路距离重新排序。

这个方案的价值是：

- 避免一开始对全量 400-800 个点做道路距离爆炸式计算；
- 先解决“哪些点放到一趟车里”；
- 再解决“这一趟车内部怎么走”；
- 是一个工程上更现实的折中方案。

它的限制是：

- 第二阶段只能优化单趟内部顺序；
- 如果第一阶段把点分错了路线，第二阶段暂时不能跨路线修正；
- 后续需要加入跨路线 relocate、swap 等局部优化。

#### 全程实际距离

从多路线插入阶段就使用 OD 缓存/百度道路距离。

特点：

- 理论上更贴近真实道路；
- 计算成本高；
- 对 OD 缓存依赖强；
- 适合点位较少或缓存较充分的场景。

### 3.6 OD 缓存与百度补算

当前项目已经接入旧系统的 OD 矩阵思路。

路线计算中的道路距离来源包括：

- OD 缓存：历史已计算过的点对，直接复用；
- 百度在线：缓存未命中时调用百度路线接口；
- 直线回退：百度失败、未配置或坐标异常时回退为直线。

这部分是理论算法落地的关键，因为真实道路距离与经纬度直线距离差异很大。

同时，项目已经加入了日志和统计信息，便于判断：

- 本次命中了多少缓存；
- 调用了多少百度在线；
- 有多少路段直线回退；
- 哪些阶段耗时较长。

### 3.7 多路线异步进度和取消

由于道路精排和百度补算可能耗时较长，当前多路线生成已改为异步任务模式。

前端点击生成后：

1. 后端创建任务并返回 taskId；
2. 后端后台执行路线规划；
3. 前端每秒轮询任务状态；
4. 页面展示真实进度；
5. 用户可点击停止按钮取消任务。

当前进度可以显示：

- 当前阶段；
- 第几趟 / 总趟数；
- 当前车辆；
- 当前趟点数；
- 已分配点数；
- 剩余点数。

这解决了之前同步接口“页面一直等待，不知道算到哪里”的问题。

### 3.8 多路线结果展示方式切换

最新实现中，多路线生成前不再选择“点位直线 / 道路折线”。

新的设计是：

- 生成路线阶段默认返回直线路段，避免展示拖慢规划；
- 结果生成后，每一趟路线可以单独切换展示方式；
- 点“道路折线”时，仅为当前这趟路线补道路折线；
- 补完后缓存到当前路线对象，再次切换不重复计算。

这让“路线规划”和“地图展示”解耦：

- 规划策略决定路线怎么生成；
- 展示方式决定地图怎么画。

这也是当前系统设计中一个重要的工程边界。

### 3.9 Excel 导出

多路线生成结果支持导出 Excel。

当前导出内容覆盖：

- 多路线汇总；
- 每趟路线明细；
- 路段信息；
- 点位顺序；
- 载重、距离、耗时、来源等字段。

这部分方便汇报、交付和线下核验。

## 4. 当前系统架构理解

当前项目可以理解为四层。

### 4.1 数据层

数据来自现有业务库，包括：

- 公司；
- 路线；
- 岗位；
- 点位；
- 流水；
- 设施点；
- 停车场；
- OD 缓存。

后续如果要产品化，需要继续梳理字段质量和数据来源，尤其是点位坐标、设施类型、垃圾量估计、车辆信息。

### 4.2 算法层

当前算法层包括：

- 单路线全路径插入；
- 多路线逐趟生成；
- 直线快速分组；
- 道路距离精排；
- OD 缓存和百度补算；
- 路线评分。

算法层当前仍以启发式为主，不是数学规划求全局最优。

这种选择是合理的，因为业务数据规模大、约束多、数据质量不稳定，启发式更容易先落地、解释和调试。

### 4.3 服务层

后端提供：

- 路线数据查询；
- 单路线优化；
- 多路线异步任务；
- 路段道路折线懒加载；
- Excel 导出；
- 路线评分接口。

### 4.4 展示层

前端提供：

- 路线与岗位工作页面；
- 多路线生成页面；
- 路线评分页面；
- 地图展示；
- 轨迹播放；
- 路线展示方式切换；
- 导入筛选点位；
- 进度展示和取消。

## 5. 当前阶段价值

当前阶段最大的价值不是已经得到一个完美路线算法，而是完成了从“历史算法材料”到“可运行工程系统”的转变。

具体表现为：

1. 历史笔记中的全路径插入思想已经工程化；
2. 旧系统中的 OD 缓存和百度算路思路已经接入当前项目；
3. 单路线优化已具备可视化和播放能力；
4. 多路线生成已具备公司级点位池输入、装载率控制和多趟输出；
5. 新增了两阶段策略，降低全道路多路线规划的计算成本；
6. 长耗时任务已从同步等待改成异步进度；
7. 展示方式从生成前参数改成生成后按路线懒加载，系统边界更清晰。

这说明项目已经从“算法回忆和复现”进入“产品化原型迭代”阶段。

## 6. 当前不足

当前项目仍然有明显不足。

### 6.1 多路线仍是启发式初解

当前多路线本质上仍是逐趟生成：

```text
生成第一趟 -> 删除已分配点 -> 生成第二趟 -> ...
```

这种方式可解释，但存在局部最优问题。

后续需要加入：

- 跨路线点位移动；
- 两路线之间 swap；
- 单路线内部 2-opt；
- relocate；
- 未分配点二次尝试。

### 6.2 垃圾量估计仍需加强

当前预计垃圾量主要依赖已有字段和简化估算。

真实业务中垃圾量受以下因素影响：

- 点位桶数和桶型号；
- 历史流水；
- 收运频次；
- 上次收运时间；
- 是否存在半车、漏收、重复收等异常。

后续需要把历史流水和过磅数据更系统地用于点位垃圾量预测。

### 6.3 时间窗尚未真正落地

历史笔记中提到过时间限制和点位可见性，但当前还没有完整实现。

后续需要考虑：

- 点位可收运时间；
- 车辆工作时长；
- 处理厂开放时间；
- 路线总时长阈值；
- 交通时段影响。

### 6.4 车辆排班仍处于基础阶段

当前已经支持一定程度的车辆排班输入，但距离真实派车方案还有距离。

未来需要解决：

- 公司有哪些车辆；
- 每辆车可跑几趟；
- 大车优先还是小车优先；
- 同一辆车第二趟从哪里出发；
- 车辆成本如何计算；
- 是否自动生成车辆排班。

### 6.5 道路距离计算成本仍高

如果大量点对没有 OD 缓存，百度补算会非常慢。

例如 459 个点，即使先分成 15 条路线，每条约 30 个点，如果每条内部道路精排需要大量点对，最坏情况下仍可能达到小时级。

因此后续必须继续优化：

- 批量预加载缓存；
- 后台补算；
- 限制道路精排点位规模；
- 缓存复用；
- 分阶段返回结果；
- 尽量避免无意义全量点对计算。

## 7. 后续规划

### 7.1 算法优化

建议下一阶段从局部优化开始，而不是直接上复杂 VRP 求解器。

优先级建议：

1. 单路线内部 2-opt；
2. 单路线 relocate；
3. 单路线 swap；
4. 跨路线 relocate；
5. 跨路线 swap；
6. 未分配点二次插入；
7. 小点量全局穷举校验；
8. 后续再评估 OR-Tools 等成熟 VRP 求解器。

这样可以保持算法可解释，也便于逐步验证每个优化点是否真的改善结果。

### 7.2 多路线约束增强

后续应逐步加入：

- 额定载重和最大载重更精细控制；
- 时间窗；
- 车辆通行限制；
- 点位收运频次；
- 处理厂容量；
- 中转站选择；
- 区域划分；
- 点位共享分区；
- 未分配原因解释。

### 7.3 地图展示增强

当前地图展示已可用，但还可以继续增强：

- 多路线在同一张地图上用不同颜色展示；
- 支持多路线整体播放；
- 展示车辆、路线、点位、处理厂等图层；
- 路线点击后高亮；
- 直线与道路折线对比；
- 展示直线回退路段并标红。

### 7.4 路线评分增强

路线评分后续可以继续从“指标”走向“解释”。

建议增强：

- 流水路线与规划路线 LCS 高亮对比；
- 命中但顺序偏离的点位展示；
- 多次往返点位识别；
- 计划外点位识别；
- 漏收点位识别；
- 路线执行稳定性评分。

### 7.5 飞书生态集成

如果未来参与飞书知识大赛，可以从以下方向接入飞书生态：

- 飞书文档：自动生成路线优化报告；
- 飞书表格：导入点位、车辆、路线结果；
- 飞书多维表格：沉淀点位库、车辆库、优化任务库；
- 飞书审批：路线变更审批；
- 飞书消息：优化任务完成通知；
- 飞书知识库：沉淀算法说明、项目公司方案、调度经验。

这部分不应为了比赛强行接入，而应围绕真实业务流程：数据导入、任务执行、结果确认、调度下发、复盘汇报。

### 7.6 司机端路线指引

司机端目前不建议作为当前主线立即实现，但可以规划。

未来形态可以是：

- 司机查看当天路线；
- 查看下一个点位；
- 一键导航；
- 点位完成确认；
- 异常上报；
- 实际轨迹回传；
- 与规划路线进行偏离分析。

这部分会让路线优化从“规划系统”进入“执行闭环”。

## 9. 阶段结论

当前项目已经具备可演示的路线优化原型。

它的特点是：

- 有历史算法依据；
- 有旧系统工程经验支撑；
- 有当前项目可运行实现；
- 已经开始处理真实业务中的 OD、地图、异步任务、导出和用户交互问题；
- 后续扩展方向清晰。

下一阶段建议聚焦两个方向：

1. 算法质量：加入局部优化和跨路线调整，让结果更接近真实可用方案；
2. 产品闭环：增强地图可视化、路线评分解释、任务报告和后续飞书/司机端协同。
