# 路线算法历史脉络

本文整理 2021 年前后垃圾收运路线优化研究的主要脉络，用于解释当前 `zhj_route` 项目为什么要重建通用路线优化能力。

原始过程记录保存在外层项目的 `notes/从头总结.md`，可读总结保存在外层项目的 `notes/路线规划项目总结.md`。本文只保留后续开发需要知道的历史结论。

## 背景

早期项目围绕“城市环卫大数据采集及应用管理”展开，目标是基于点位、车辆、停车场、处理厂、距离、时间窗口和通行条件等数据，自动生成垃圾收运路线。

当时先理解和调试清华方面提供的算法，之后逐渐形成自研插入式算法，并尝试接入 Java 后台系统。后续老产品化项目实际落地的是“单条路线点位顺序优化”，多路线、车辆排序、点位可见性等能力没有完整落地。

## 历史阶段

### 1. 清华原始路线合并

清华原始算法更接近路线合并：

1. 每个点位先独立成为一条路线。
2. 点对按距离从小到大排序。
3. 若某点对可以连接两条路线的尾和头，就尝试合并。
4. 合并后检查容量和时间等约束。
5. 从候选路线中选择满载率较高或效果较好的路线。

代表脚本：

- `saving_main.py`
- `fixcode.py`
- `oldmethod.py`
- `oldmethodwithdifferentrate.py`
- `randommethod.py`

这个阶段的关键成果不是最终算法，而是理解清华算法、建立可视化、增加统计，并用随机方法质疑算法效果。

### 2. 自研全路径插入

后续转向自研插入式算法：

```text
路线初始为：起点 -> 终点
遍历所有未加入点位
遍历当前路线的每一段 [A, B]
计算插入 P 的新增距离：d(A, P) + d(P, B) - d(A, B)
选择新增成本最低的点和插入位置
重复直到容量、时间或其他约束触发
```

这个过程经历了三个概念：

- 圆形：从当前点找最近点，类似最近邻。
- 椭圆：固定当前点和终点，找插入增量最小的点。
- 全路径插入：对路线所有段尝试插入，选择全局最小增量。

最终更合理的是全路径插入，因为它允许新点插入已有路线中间，不局限于路线末端。

代表脚本：

- `newmethod.py`
- `newMethodWithRate.py`
- `simpleMethod.py`
- `completeMethod.py`
- `easymethod.py`

### 3. 约束与调度探索

历史笔记中已经讨论过很多后续能力，但没有完整落地：

- 多路线生成：一次性给全部点位和车辆，生成多条路线。
- 车辆排班：大车优先、小车优先、同车多趟、车辆轮流跑等。
- 点位可见性：允许时间窗口、禁止时间窗口、车辆通行条件。
- 城市分区：按中转站或处理厂距离划分收运区域。
- 真实路线学习：从历史司机路线中提取单位距离收运量、插入成本、路线性价比等指标。

代表脚本和笔记：

- `carlistcontrol.py`
- `timeControl.py`
- `java数据提取`

这些内容说明项目真正想解决的是多车辆、多路线、多约束的路径规划，而不是单路线排序。

### 4. Java 接口化尝试

后期开始把算法包装成 Java 后台可调用的形式：

- `py4java_tsinghua.py`：清华原始算法接口版。
- `py4java_zhj.py`：自研插入算法接口版。
- `py4java_zhj_ring.py`：末端/圆形策略的简化变体。

接口化阶段的变化：

- 输入从散乱 Excel 变成标准数据集。
- 输出从调试 CSV 和图片变成 Java 可读取 JSON。
- 开始带车辆编码、路线距离、容量、时长等信息。

这说明项目最后已经接近工程化，但约束处理仍依赖默认值、分组和补派，未形成稳定通用算法。

## 对当前项目的结论

1. `zhj_route` 不应直接复制历史脚本，而应吸收历史算法思想。
2. 单路线算法应以“全路径插入”为第一版核心。
3. 多路线算法应在单路线外层增加车辆循环、剩余点池和约束判断。
4. OD 矩阵、地图补算、路线渲染是工程落地必需能力，不能只实现排序函数。
5. 老系统只落地了单路线优化，新项目应把目标提升为通用路线优化模块。
