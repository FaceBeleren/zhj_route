## 用户当时的多路线思想

多路线的核心目标：

```text
给定一个公司的一批待收运点位、一批车辆、停车场/中转站/处置场和业务约束，
一次性生成多条路线，尽量遍历所有点位，并解释未分配原因。
```

历史递进需求：

1. 只给点位信息和一种车型：生成该车从停车场到处理厂的多条路线，遍历所有点位。
2. 加入车辆信息：考虑车辆第一趟和后续几趟的出发点、到达点，并根据当前状况选择不同处理厂。
3. 加入全部车辆型号：选择部分车辆，生成低成本车辆规划方案。
4. 加入点位频次、车辆通行条件、每趟路线时间因素、通行时间限制、收运点处理能力。
5. 因每趟路线都会更新剩余点位和剩余垃圾量，所以必须有具体排班顺序。

历史派车思考：

- 大车优先可能减少远距离往返次数，但后期可能被迫跨区域收尾；
- 小车优先算法时间成本较低，路线较短，但可能浪费多次往返；
- 同一辆车跑完第一趟后，第二趟起点可能是上一趟终点；
- 也可以所有车辆先跑第一趟，再安排第二趟；
- 派车顺序会影响剩余点池，从而影响最终路线结果；
- 不应一开始就把排班做成黑盒，至少要能解释为什么先派这辆车。

历史点位选择思考：

- 圆形：从当前点找最近点，类似最近邻；
- 椭圆：固定当前点和终点，找插入当前点后增量最短的点；
- 全路径插入：对当前路线的所有段尝试插入，选择新增距离最小的点；
- 最后较合理的是全路径插入，因为它允许点插入路线中间，不局限于末端。

历史阈值/停止条件思考：

- 第一条路线何时停止是多路线的第一个关键问题；
- 可按额定载重、最大载重、目标装载率、预计总时长、路线距离、处理厂容量等截停；
- 如果当前车辆已经接近满载，不应为了少量垃圾绕很远；
- 但也要警惕：一个远点附近可能还有很多点，单纯按新增成本可能过早拒绝跨区域启动点。

历史时间限制/点位可见性：

- 每次添加一个点后计算当前路径属性，尤其是时间；
- 若累计量达标则输出路径；
- 点位可见性至少包括允许时间窗口、禁止时间窗口、车辆可通行条件、点位处理能力。

历史区域划分：

- 方案一：每派一辆车后，统计剩余点位到各中转站距离加和，派车去加和最短的场站；
- 方案二：先按点到场站距离分区，每个点归属最近场站；
- 可以有共享分区：如果点到两个场站距离都低于阈值，可作为共享点池。

## 当前实现状态

当前 `repo_zhj_route` 已经实现：

- `路线详情` 页面：公司、路线/岗位、规划点位、流水、单路线优化预览；
- `多路线生成` 页面：公司级点位池、点位筛选、场站起终点、容量目标、多路线预览；
- `路线评分` 页面：公司评分、路线评分、流水评分、F1/LCS 评分解释；
- 公司点位池只取 `ljszy_facility_info.facility_type=6` 的收集点；
- 停车场、中转站、处置场来自 `ljszy_facility_info` 的类型 `4/2/5`；
- 中转站和处置场绑定关系来自 `ljszy_transfer_station_configuration`；
- 垃圾量估算来自 `ljszy_facility_container_info` 和 `ljszy_base_config.liters_per_ton`；
- 多路线生成当前用 Haversine 经纬度直线距离，尚未接入真实道路 OD。

## 继续多路线算法时的建议顺序

不要一次性做所有约束。建议按下面顺序小步落地：

1. 明确未分配原因
   - 最大趟数耗尽；
   - 预计垃圾量缺失；
   - 缺坐标；
   - 单点超过车辆最大载重；
   - 时间窗不可行；
   - 无可用场站。

2. 改进停止条件
   - 当前已有目标装载率；
   - 增加最大载重；
   - 增加单趟最大距离/最大时长；
   - 输出“为何停止本趟”。

3. 接入 OD 矩阵
   - 先封装距离服务接口；
   - 缓存点对道路距离和时长；
   - 没有 OD 时回退直线距离；
   - 前端明确显示当前距离来源。

4. 单路线局部优化
   - 在全路径插入结果后做 2-opt；
   - 再做单点 relocate、swap；
   - 每次优化都输出节省距离和改动点。

5. 多路线局部优化
   - 跨路线 relocate；
   - 跨路线 swap；
   - 平衡装载率、距离和未分配点。

6. 车辆排班
   - 先支持用户给定车辆顺序；
   - 再支持大车优先/小车优先/成本优先；
   - 最后再考虑自动选择车辆组合。

7. 时间窗和点位可见性
   - 增加点位服务时长；
   - 增加车辆最大工时；
   - 增加可服务时间窗；
   - 增加车辆和点位通行标签匹配。

8. 再评估 OR-Tools
   - 当上述模型稳定后再引入；
   - OR-Tools 不应直接替代可解释业务模型；
   - 需要保留当前启发式算法作为快速初解和降级方案。

## 新对话不应忘记的原则

- 本项目不是只做算法题，而是算法落地到环卫业务系统。
- 理论路线短不等于业务可执行。
- 当前用户非常重视历史思路的延续，不要随意推翻 OneNote 里的思考。
- 但也要客观指出：历史算法是合理启发式，不是全局最优算法。
- 每个功能要可解释：为什么这么排、为什么这个点未分配、为什么这条路线低分。
- 地图、OD、数据质量和版本管理与算法同等重要。
- 未来可能接飞书知识大赛，注意沉淀文档、报告、机器人、多维表格和审批任务这些飞书生态点。
